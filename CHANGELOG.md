# CLI changelog

## 0.0.22 — 2026-11-12

- **`--strict-anon` refuses an identified saved run on every path, including an agent job.** The check no longer skips an upload that carries an `agent_job` field. A run saved with `--strict-anon` still uploads. Agent children save that way, so a normal agent upload is unchanged. An identified run is not posted and gets no upload marker.
- **A saved run signed with this machine's long-term key is identified even when it has no `fingerprint_hash`.** The JWS header `jwk` is compared with the persistent public key. If that key file is not already on disk, this part of the check is skipped and the key is not created. An older non-strict save in that shape is refused under `--strict-anon` (no POST, no sidecar) and, in a no-path `submit`, skipped with the same warning as any other identified run.
- **llama.cpp bench rows take decode tok/s from the server timings (KFM-045).** `chat-short`, `chat-long`, `long-context-decay` and `concurrent-decode` use llama-server `timings` for `decode_tps` on every llama.cpp row, including a row whose chunks are one token each. `predicted_per_second` is that rate. When it is 0 or missing, the fallback is `(predicted_n - 1) / (predicted_ms / 1000)`, and only when `predicted_n` is at least 2 and `predicted_ms` is above the server's 1µs floor. Otherwise the rate is left unset. llama.cpp fecdc81 (`tools/server/server-common.h`) does not put the first generated token inside `predicted_ms`: that token comes from the last prompt batch, and the server's own rate uses `n_gen - 1`. Dividing by a duration at the 1µs floor is not a rate. The chunk figure stays in `extras.decode_tps_stream`. `extras.decode_tps_source` is `server_timings`, `server_predicted_n_ms`, or `stream_chunks`, and the same field is on each `concurrency_curve` point. A batch whose streams used more than one method lists them joined with `+`. The field rides the existing extras object. There is no result-schema change. `decode_p50_latency_ms` and `decode_p95_latency_ms` still come from the chunk gaps. `agent-trace`, and the drivers other than llama.cpp, still use the chunk formula `(text chunks - 1) / (time from the first text chunk to the last)`. That formula is in v0.0.3, so every version before 0.0.22 is affected. On run `r_91l46y770n8` the reported figure was about 4.6–4.7% low. The p50 of 13.86 ms recomputes to 72.15 tok/s. That 72.15 is a recomputation, not a second measurement. Other rows were not measured.
- **concurrent-decode gives each llama-server slot the step context (KFM-044).** An explicit `--parallel` turns unified KV off on llama.cpp build 12157, so a slot was the step context divided by the stream count and a filled prompt overflowed it. When the sweep owns `-c`, that context is now parallel times the step. A `-c`, `--ctx-size` or `--kv-unified` already in the plan is left as written, and a slot smaller than the prompt plus 256 output tokens is a warning. The workload reads `n_ctx_slot` and `kv_unified` from the server and records them on the result. It does not send a completion when the prompt plus max tokens exceeds `n_ctx_slot`.
- **A WSL agent can find pipx and uv when the logon task's PATH does not (KFM-043).** `wsl.exe --exec` does not load `~/.profile`, so `~/.local/bin` and `~/.cargo/bin` are not on PATH and 0.0.14–0.0.21 recorded a pipx or uv install as manual and left the agent running. Those two directories are now checked after PATH. A system or externally managed Python is still not updated in place. Auto-update stays on by default. Nothing new is collected or uploaded, and consent is unchanged.
- **`llm-speed submit` says why nothing was uploaded (UX backlog row 68).** Answering no to `Upload the N runs listed above? [y/N]` (Enter, `n`, EOF, or Ctrl-C) prints `Not uploaded: you answered no.` With no terminal and no `--yes`, the question is not asked and the CLI prints `Not uploaded: no terminal to confirm; pass --yes to upload the listed runs.` `Skipping upload (no consent).` is printed only when the consent gate refuses. An empty cache, and a cache whose runs are all already submitted, adds "Run `llm-speed bench` to create one." after the existing line. `submit --help` names the consent file `~/.config/llm-speed/consent.json` (the default of `CONFIG_DIR / "consent.json"`; `$LLM_SPEED_CONFIG` still moves that directory). `--yes` still answers only the batch question and does not grant consent. The consent prompt and its `[Y/n]` behaviour are unchanged. Local saves are unchanged. Nothing new is collected or uploaded.

## 0.0.21 — 2026-11-12

- **`llm-speed submit [PATH ...]` uploads runs that were saved locally and never submitted.** With one or more paths, each file is uploaded by the same code as `llm-speed bench --resume PATH` (the saved JWS is verified locally and posted unchanged). With no path, the CLI lists unsent runs in `~/.cache/llm-speed/runs/` (timestamp, model, hardware) and offers them through the existing consent prompt. A local sidecar `<file>.json.uploaded` records a successful upload so a later no-arg `submit` skips it. The sidecar is never uploaded, and the saved run JSON is not modified. No new upload or collected field.
- **After a successful upload** the CLI prints `Saved locally: {path}` next to `View and share your result: {url}`.
- Consent prompt wording and behaviour are unchanged: an empty answer on a TTY is yes, and a non-TTY refuses unless consent was already recorded or `--strict-anon` is set. A named path with no consent file and no terminal does not upload. After consent, a no-path `submit` asks `Upload the N runs listed above? [y/N]` (default no, including under `--strict-anon` on a terminal). `--yes` answers only that question and does not grant consent. `--strict-anon` sends no API key, no User-Agent and no credit, and refuses a saved run that still has `fingerprint_hash` or `storage` (no POST, no sidecar). Local save behaviour is unchanged. No new auto-consent.
- **Prompt fill uses a real token count (KFM-031).** `long-context-decay` and `concurrent-decode` grow the prompt until the model's tokenizer, or llama-server's `/apply-template` and `/tokenize`, is within 2% of the requested length (at least 32 tokens). A 16K target no longer stops near 12K on a tokenizer that uses more than 4 characters per token. With no counter, the 4-character filler remains. `prompt_tokens` on the result is the backend's count, or the measured count when the backend reports none. The prompt is not logged and is not sent anywhere except that local server. Prompt fill only changes how accurate the existing `prompt_tokens` value is. Two new integer keys in concurrent-decode extras: `extras.prompt_tokens_actual` and `extras.concurrency_curve[].prompt_tokens`.
- **`exact_llama_build` and `max_llama_build`.** A preset can pin one llama.cpp build or a maximum, next to `min_llama_build`. The CLI and the Worker both reject a window that disagrees with itself. A known mismatch fails the run with a message that names both builds, records a failed fit result (`llama_build_mismatch`), and does not run a different binary. Auto-install still only installs the pinned prebuilt; if that build is outside the window it is not installed instead, and no older build is downloaded. `--force` does not override a reported build that misses `exact` or `max`.
- **`concurrent-decode` can be named in a preset.** `workloads_by_ctx` and a model context step accept it. `env.LLM_SPEED_CONCURRENT_STREAMS` (for example `1,4,8`) and `env.LLM_SPEED_CONCURRENT_PROMPT` (for example `16384`) replace the fixed batch list and the ~1K prompt. The llama.cpp step's `--parallel` is at least the largest stream count. Per-stream tok/s stays `decode_tps` / `extras.concurrency_curve[].per_stream_tps`; the total stays `aggregate_tps`. Two new integer keys in concurrent-decode extras: `prompt_tokens_actual` and `concurrency_curve[].prompt_tokens`. Streams outside 1-64 and prompts outside 1024-1048576 are `schema_invalid` (CLI and Worker), not a silent fallback.
- **Also in this release: the ssd_stream floor-probe test fix (c6d8ece6, KFM-041).** `tests/cli/test_storage_preset_e2e.py` runs a real preset sweep. While llama-server loads, that sweep's floor check calls `shutil.disk_usage` and psutil's available memory. release-pypi run 42744221917 failed the first two tests once with exit 14 `disk_below_floor` (the runner was under the 5 GB disk floor), then passed on the same SHA. Those tests now monkeypatch the two probes to fixed values. `floor_breach` itself is unchanged and still covered, including its default probe path with the probes monkeypatched. One test sets the mocked free disk below the floor and expects exit 14 `disk_below_floor`. Consent, `--strict-anon`, local save and `--no-upload` are unchanged. No upload field is added. The package version stayed 0.0.20 when that fix landed; it ships in 0.0.21.

## 0.0.20 — 2026-11-10

- **Split / multi-part GGUF files load as one model (KFM-040).** A llama.cpp model shipped as `name-00001-of-000NN.gguf` was handled as whichever single file the path, the download, or the size check happened to see, so llama-server either exited on a missing part or was handed an HF blob hash and never opened the other shards. The set is now one model: every shard must be present (a missing one is named and the server is not started), every shard is downloaded, the fit / VRAM check uses the sum, and `-m` is the first shard with its filename intact. Preset entries can list the shards in `files`, each with its own `sha256`, or name any one shard in `file`; `bytes` is the total. Every supplied hash is checked before llama-server starts, and a mismatch names the shard and does not start the server. A split missing a shard hash is refused like a single-file GGUF missing `sha256`. `extras.model_file` records the shard basenames and `extras.model_file_bytes` is the sum. No new upload field. Ollama is unchanged (it serves an installed tag, not a GGUF path).
- **GGUF pins are exact digests (R-153, R-154).** A sha256 is 64 lowercase hex characters and nothing after them; a trailing LF or CRLF is rejected by the preset schema, signed-preset checks, and Worker publish. An invalid, missing, or mismatched required pin stops the launch and is never recorded as verified. A one-item `files` list is checked as that file's pin and must agree with a top-level `sha256` when both are set. Duplicate and extra shard names are refused. `bench --model` does not hash the file, and `--no-verify` does not mark a run hash-verified.
- **A `files`-only preset downloads the GGUF name, not the entry object (R-155).** A one-item `files` list with no top-level `file` used to pass `str` of the whole `{file, sha256}` object to the Hugging Face fetch and cache lookup. Both use the validated filename. The file is hashed before llama-server starts.
- **More shapes that are not a digest (R-156).** Uppercase, short, long, and whitespace (leading, trailing, and internal spaces, tabs, LF, and CRLF) are rejected on both the top-level `sha256` and each `files` entry. The CLI and the Worker share those vectors.
- **`--n-cpu-moe` was already passed through.** `llm-speed bench --llama-args='--n-cpu-moe N'` (and `$LLM_SPEED_LLAMA_ARGS`, and a preset entry's `n_cpu_moe`) is appended to llama-server and recorded in the existing `extras.llama_server_args`. Nothing new was added for it.

## 0.0.15 — 2026-11-01

- **Upgrade note:** Machines on 0.0.14 need one manual upgrade to 0.0.15 (`pipx upgrade llm-speed`, `uv tool upgrade llm-speed`, `brew upgrade meadow-kun/tap/llm-speed` or `pip install -U llm-speed`); after that, auto-update keeps them current.
- **Fix: auto-update never ran without the `packaging` module (0.0.14).** `llm-speed` doesn't depend on `packaging`, so pipx, uv and brew installs usually use the built-in version parser, whose versions printed as `_RegexVersion(key=...)`. The update check then compared that text, decided nothing was newer, and printed `Up to date (latest on PyPI: _RegexVersion(...))`; no installer ever ran (and none could get that text). Versions now print and are cached as the plain canonical string. 0.0.14 installs without `packaging` need one manual upgrade to 0.0.15 (KFM-036).
- **Installer gate fixes (0.0.14 run):** metadata checks run isolated (`python -I`) from the row's sandbox, so an `llm_speed.egg-info` in the current directory can't shadow the install (it failed every pip/pipx/uv upgrade row with "could not install PREV"); the workflow builds the candidate wheel from a copy outside the checkout and runs the gate from an empty directory; brew rows remove every keg (`brew uninstall --force`) and check none is left, so the brew auto-update row no longer skips as "already installed".
- **Fix (Security Desk R-140): the in-use marker can't be lost to a cleanup race.** `InUse` keeps its `<config>/in-use/<pid>` file only if, once locked, it is still the file at that path; a stale file from a reused PID that a cleaner has locked is replaced, and cleaners unlink only the file they hold locked (retries for about 1 s, then runs unmarked).

## 0.0.14 — 2026-11-01

- **Auto-update, on by default (Boss, via GM).** At most once a day a command starts a detached background check of `https://pypi.org/pypi/llm-speed/json` and, if there is a newer release, installs it with the installer this copy came from: `pipx upgrade llm-speed`, `uv tool upgrade llm-speed`, `brew upgrade meadow-kun/tap/llm-speed` (kegs installed from that tap), or `python -m pip install --upgrade llm-speed==<version>` inside a writable virtual environment. Only venv pip pins an exact version; pipx, uv tool and brew upgrades are verified by reading the installed version back (only a newer version counts). The command never waits for it; offline is silent. The next run prints `Updated llm-speed A -> B` once (stderr). Installs it can't update (system or externally managed Python, unwritable site-packages, a source checkout) print the right upgrade command once a day instead. Off with `LLM_SPEED_DISABLE_AUTOUPDATE=1` or the new `llm-speed config set auto_update false`; also off in CI and when stdout isn't a terminal. Machines on 0.0.13 or older have no updater and need one manual upgrade.
- **The agent updates itself between jobs** (`llm-speed agent run`, on by default; never during a claim or a run), then restarts in place with `os.execv` (same PID and arguments; Homebrew through `opt/llm-speed`). If the new version won't start it exits 75 so systemd / launchd / the WSL2 task restart it. `cli_version` is still recorded on every result.
- **Fix: Homebrew agent service survives `brew cleanup`.** `agent install` registered the launchd job (and the systemd unit / WSL2 task) with the versioned `Cellar/llm-speed/<version>` Python, which the next `brew upgrade` + cleanup deletes. Every registration now uses the stable `<brew prefix>/opt/llm-speed/libexec/bin/python`, and an existing Cellar-path plist / unit is rewritten the next time `agent install` or a successful update runs (systemd: `daemon-reload` only, nothing is restarted). Known limits: KFM-036.
- **Security Desk fixes (R-136 to R-139).** The install is never replaced while another llm-speed process runs: every command (bench, MCP server, ...) and each agent job holds a locked marker in `<config>/in-use/<pid>` (markers of exited processes are removed); an update then records `busy` and retries in about an hour, and `llm-speed update` says so. The background worker waits for the command that started it on every OS, not only Windows. No background check starts if its daily time can't be saved, and `agent run` keeps its own once-a-day limit in memory; an idle agent whose files were updated by another process restarts into the new version before its next job. The installer gets the canonical version string. The test hook rejects UNC / `//` paths and symlinked components and gives the installer a private copy of the wheel only. Docs: pipx and uv update from the index they were installed from; the pre-release opt-in only affects venv pip; `--strict-anon` doesn't turn the check off (PRIVACY.md).
- **`llm-speed update [--check]`** replaces the `self-update` stub (kept as an alias); the stub's request to the llm-speed API's suite manifest is gone.
- **Safety:** only the package `llm-speed` from PyPI or the meadow-kun tap, at a version from PyPI's JSON validated with `packaging.version` (strict regex fallback); no downgrades; yanked releases skipped; pre-releases only with `config set auto_update_prereleases true`; https only, no redirects, 10 s timeout, 4 MiB cap; index / find-links / constraint variables and pip/uv config files removed from the installer's environment; argv lists from absolute paths, never a shell; a lockfile allows one update at a time. Nothing is sent to llm-speed servers (docs/PRIVACY.md). Upload, consent, `--strict-anon` and local saves are unchanged. Security Desk review pending.
- **Installer gate:** `scripts/check-installers.sh` / `.ps1` gain an `autoupdate` scenario: with `--auto-update-wheel` / `-AutoUpdateWheel` the candidate wheel is installed with pip, pipx and uv (Linux, macOS, Windows) and must update itself in the background to a `.post1` copy through a test-only hook (both `LLM_SPEED_UPDATE_TEST=1` and a local `file://` wheel required); Homebrew installs it from a throwaway local tap (`llm-speed-gate/local`, never meadow-kun/tap), the formula is switched to `.post1`, and the background updater must `brew upgrade` to it. The installer-gate workflow builds the wheel from the release tag in each job and passes it, so every installer is checked on every OS next to the fresh and upgrade-from-PREV rows; without the wheel (PREV >= 0.0.14) the PREV install's `llm-speed update` must reach NEW. New helper `scripts/make-update-test-wheel.py`, exported to the mirror with the gate. Known limits: KFM-036.

- **Security Desk N-5: the API key only goes to api.llm-speed.com or a host you opt in to** (KFM-029). With `--api-base` or `$LLM_SPEED_API` pointing anywhere else, `bench`, `bench --resume` and `bench --preset` now upload *without* the `--api-key` bearer (an anonymous signed upload) and print a note naming the host and the opt-in, instead of sending the key after a warning. Opt in with the new global `--allow-token-to-host HOST` or `LLM_SPEED_ALLOW_TOKEN_HOST=HOST`, matched exactly against the normalized host (`host[:port]`, case, trailing dot and default port ignored; no wildcards or subdomains). `llm-speed agent enroll` with a non-default queue that comes only from `$LLM_SPEED_API` stops with exit 2 (enroll with `--api-base URL` or the opt-in); an old enrollment with no saved server doesn't follow a non-default `$LLM_SPEED_API` without the opt-in. The enrolled queue counts as opted in: the agent's job processes get `LLM_SPEED_API` and `LLM_SPEED_ALLOW_TOKEN_HOST` for exactly that queue, and any inherited opt-in is dropped.
- **Security Desk N-6: signed uploads use the JWS alg `Ed25519`, with no `SecurityWarning`.** joserfc 1.7 printed `SecurityWarning: EdDSA is deprecated via RFC 9864` on every signed upload, because the header said `EdDSA`. 0.0.10 emits `alg: "Ed25519"`, the RFC 9864 name for exactly what the CLI signs with (same Ed25519 key and signature bytes; only the header name changes). A server that answers `unexpected alg` (an older self-hosted server that only knows `EdDSA`) gets the same payload re-signed once as `EdDSA`, never with a different key and never for any other error; nothing is saved or printed, and one log line without values says the server is older. `EdDSA` is signed and verified through a private joserfc registry whose `EdDSA` entry is Ed25519-only and carries no warning (joserfc's global registry is untouched). Local verification (`bench --resume`) accepts both `EdDSA` and `Ed25519` headers with Ed25519 keys only, so runs saved by earlier versions still verify; the server and the legacy Python verifier (`api/verify.py`) accept both names. Pinned by `tests/cli/test_signing_alg.py` and `worker/tests/cli-jws.test.cjs` (a CLI-signed token verified by the server's own `verifyJwsToken`).
- **Security Desk R-69: dependency bumps.** Bump certifi to 2026.10.19+ (drops the compromised emSign/eMudhra intermediates, GHSA-6q48-6c7w-9gw2), cryptography to 50.0.0+, idna to 3.15+ and joserfc to 1.6.8+, and anyio to 4.14.2+ (PYSEC-2026-4024/4025); lock and Homebrew formula updated (R-69).

### `llm-speed agent`

- **Gates (must-fix before pairing a GPU box that keeps models resident):**
  - Busy = the GPU is working: utilization sampled `busy_samples` (5) times over `busy_window_s` (15 s), busy when the mean or most samples are above `busy_util_pct` (15). NVIDIA via `nvidia-smi`, Apple Silicon via `ioreg` "Device Utilization %". The 0.0.9 `gpu_busy_mib=4096` (raw VRAM used by other processes) is gone: an idle :8080 server or ComfyUI holding 20 GB no longer blocks every job (KFM-023).
  - Free VRAM / unified memory / disk are checked after the claim against what that job's preset needs on this machine: the largest model file it would load + the preset's `memory_headroom_mib` (capped at the device minus 1 GiB), and the files still to download + the preset's `disk_margin_gb`. A shortfall hands the job back (`gate_closed`) with the exact reason in `agent status` and waits ~5 min. Replaces the fixed `min_free_mem_gb=24` / `min_free_disk_gb=30`. Per-machine overrides: `vram_margin_gb`, `mem_margin_gb`, `disk_margin_gb`, `need_free_vram_gb`, `need_free_mem_gb`, `need_free_disk_gb`; `agent run --busy-util-pct/--busy-window-s/--busy-samples`. Old keys in a 0.0.9 config are ignored, and `agent config OLDKEY` says what replaced it.
  - `LLM_SPEED_AGENT_INSECURE_OK=1` no longer does anything: the https / loopback check on the queue URL can only be relaxed by the test suite (a module constant a fixture patches).
  - An agent enrolled with a self-hosted `--api-base` sends the preset child's result uploads to that same server (`LLM_SPEED_API` set for the child only), never to api.llm-speed.com.
  - No change to `cli/schemas/llm-speed-preset-1.schema.json` or the packaged presets.
- **Busy check fails closed (KFM-027):** an NVIDIA GPU whose utilization can't be read (`[N/A]`, `[Not Supported]`, empty output, nvidia-smi error or timeout, or one of several GPUs unreadable) now counts as busy, and `agent status` says `GPU utilization unreadable; treating as busy (...)`. Before, the agent treated it as not busy and could take the card while it was in use. Apple Silicon is unchanged. With several GPUs the busiest one counts; CRLF output is parsed.
- **Busy reader under WSL2:** under WSL (`WSL_DISTRO_NAME` or a `microsoft` kernel) utilization comes from the Windows `nvidia-smi.exe` first (`/mnt/c/Windows/System32/`, then `wslpath` / Windows PATH), then `/usr/lib/wsl/lib/nvidia-smi`, then `nvidia-smi`, so Windows-side games and ComfyUI make the agent back off. New `agent config nvidia_smi PATH|off|auto` pins the binary. This release has no WSL service installer.
- **`agent install` / `enroll` without `--label` works again (KFM-024).** 0.0.9 sent `"label": null`, which the queue rejected with `400 label invalid (64 chars max)` until the 2026-10-22 server fix (the queue now treats `null` as no label, so existing 0.0.9 installs pair without `--label` too). The CLI now generates `<chip-slug>-<4 random chars>` (e.g. `apple-m3-ultra-7f3k`, `rtx-5090-a91c`; at most 40 chars; from the chip / GPU name or `<os>-<arch>` only, never hostname, username or paths), saves it in the agent config so re-pairing keeps it, and leaves the key out when there is none. `--label` still wins and, like `agent config label`, is checked locally against the queue's rules (1-64 chars, not path-like) with a clear error before any request.
- **Token store falls back to a file when the Keychain can't take it (KFM-025):** if the macOS login Keychain can't take the machine token (locked Keychain in an ssh / remote-helper / no-GUI session: "User interaction is not allowed", -25308), enroll now writes it to `~/.config/llm-speed/agent/token` (0600, dir 0700) in the same process instead of failing, so the once-only pairing is not burned, and the launchd service reads it without an unlocked Keychain. A Keychain write only counts after it reads back. The store used is recorded as `token_store` in the agent config (never the token); the runner reads that store first, then the other. `--token-store auto|keychain|file` on `enroll` / `install`. `agent status` and `llm-speed doctor` say which store holds the token. If no store works, enroll prints the cause and the next step (revoke the machine id, `agent install` again) instead of a bare `error:`.
- **Enrolment tokens for `agent enroll|install` (security retest R-8).** `--enrolment-token-file PATH` (a regular file you own, mode 0600/0400; group/other-readable, symlinks and malformed contents refused with exit 2, the path and value never echoed) or `$LLM_SPEED_ENROLMENT_TOKEN` (removed from the process environment on read; also stripped from every benchmark child's environment). Sent once as `enrolment_token` in `POST /v1/agent/pair`, never logged (`lse_` values are redacted like `lsa_` tokens, and so are `lsn_` nonces), never stored, forgotten after the request. `--enrolment-token TOKEN` on the command line is refused without echoing it. A 401 `invalid_enrolment` stops enrolling and is not retried without the token. After the queue takes it, enroll says the file can be deleted (or the variable unset), without printing the path. On Windows the owner/mode check is skipped with a note.
- **Job upload nonce (security retest R-9 / F5, KFM-030).** A claim may carry a per-assignment `upload_nonce` (`lsn_` + 32 lowercase hex) next to the `asg_` + 16 hex `assignment_id`; both are format-checked, and a malformed one rejects the job as `bad_field:upload_nonce` without echoing it. Every result upload of that job then puts `"agent_job": {"assignment_id", "upload_nonce"}` inside the signed JWS payload (exactly those two keys; not a header, not outside the JWS), so the queue can tie each upload to the job it issued. The nonce reaches the job's `bench --preset` process only through an inherited pipe (`LLM_SPEED_AGENT_JOB_FD` holds the descriptor number), is read once and closed before any per-cell process starts, and is never in argv, an environment value, a file, the job log, saved runs, `uploads.json`, status files or the job result, nor printed or logged; the saved per-cell JWS is unchanged and each upload is re-signed in memory with a fresh strict-anon key. Only strict-anon uploads to the queue that issued it carry it; `bench` by hand, `bench --resume` and other uploads never do, and a saved payload that already contains `agent_job` is not re-uploaded.
  - Claims declare `"features": ["upload_nonce"]` (Security Desk R-36), and the queue sends a nonce only to a claim that declares it, so 0.0.9 and other builds without this change never get one. A queue that refuses the key (`unknown field: features`) gets one more claim without it, and the agent stops sending it until restart. An `upload_nonce` in a claim never fails it, even when this build can't use it.
  - A claim without a nonce, or with one that can't be used, runs and uploads exactly as before (never a rejection), and the agent log says once, without values, "this job had no upload nonce from the queue; its results upload without one" (or that the queue's nonce could not be used). A 400 `invalid agent_job` fails the job (`agent_job_refused`, never `partial`): the upload is not retried without the field, and the job's remaining runs are marked in `uploads.json` so no later run sends them bare. No flag or setting.

## Unreleased / installer

- `scripts/install.sh` (https://llm-speed.com/install.sh) installs **or upgrades**: `--version X.Y.Z` / `LLM_SPEED_VERSION` pins a release (default latest), `--extras LIST` / `LLM_SPEED_EXTRAS`, `mlx` added automatically on Apple Silicon unless `--no-extras` (not under Rosetta), `--dry-run` prints the plan and changes nothing. Existing installs are found in pipx (classic and uv backend), uv tool, pip --user, Homebrew or anywhere on PATH. pipx installs are upgraded with `pipx upgrade` when that can work, else `pipx uninstall` + `pipx install 'llm-speed[extras]==VER'`; if pipx still refuses (uv backend: "not created in this session") the installer removes only `<pipx venvs>/llm-speed` after safety checks and reinstalls. Never `pipx install --force`. Afterwards `llm-speed --version` on PATH must match, else every copy on PATH is listed with the fix and the installer exits 1. Homebrew / pip --user copies are never removed. POSIX sh (dash-tested, shellcheck-clean). KFM-022.
- Installer hardening (security baseline L-5/L-6, 2026-10-22): every download is `curl --proto '=https' --tlsv1.2` (GNU wget: `--https-only`); the uv bootstrap is pinned to uv 0.13.1's installer URL and refuses to run unless its SHA-256 matches the value embedded in the script; the whole flow runs from `main "$@"` on the last line, so a truncated `curl | sh` download runs nothing.
- Redirects stay on https (security retest N-3, 2026-10-22): GNU wget's `--https-only` turned out to cover only recursive downloads and still followed an https → http redirect, so without curl the installer now runs wget with `--max-redirect=0` and follows each redirect itself, refusing any hop that isn't `https://` (10 hops max). BusyBox wget, which can't do that, is refused with "install curl". curl (`--proto '=https'`, which also covers redirects) is still preferred and unchanged; the uv installer SHA-256 check is unchanged.
- Docs and doctor hints no longer suggest `pipx install --force` / `pipx install -U`; they point at the installer, `pipx upgrade llm-speed`, or `pipx uninstall llm-speed && pipx install llm-speed`.

## 0.0.8 — 2026-10-22

[Published release](https://github.com/meadow-kun/llm-speed/releases/tag/v0.0.8) · [PyPI](https://pypi.org/project/llm-speed/0.0.8/)

Launch-readiness for day-one runs of large MoE models (first target: Recursive Flint 40B-A2.5B on RTX 3090/4090/5090 and Apple Silicon).

- **Load and out-of-memory failures are results, not crashes.** Each failed workload carries `extras.failure_kind` (`oom`, `unsupported_arch`, `load_failed`, `load_timeout`, `server_unreachable`, `runtime_error`). The llama-server log is kept locally (`~/.cache/llm-speed/logs/llama-server-last.log`, never uploaded) and the matching line (e.g. `cudaMalloc failed: out of memory`) goes into the error. After a load failure the remaining workloads are recorded as `skipped_after_load_failure` instead of re-loading the model each time. Failure-only runs still stay local unless you pass the new `--upload-failures`.
- **Peak memory per workload:** `extras.peak_vram_mib` (rounded to 16 MiB) from `nvidia-smi` device-wide sampling on NVIDIA, or MLX's own peak allocation on Apple Silicon; `extras.peak_vram_source` says which.
- **Time to first answer:** `extras.time_to_first_answer_ms` (first non-reasoning token), `extras.reasoning_tokens_est` and `extras.answer_started` for single-stream workloads. `ttft_ms` is unchanged (first token of any kind).
- **llama-server passthrough:** `--llama-args='-c 4096 -ngl 999 --n-cpu-moe 20'` (or `$LLM_SPEED_LLAMA_ARGS`) is applied when the CLI starts llama-server and recorded as a declared label when reusing `LLAMA_CPP_SERVER_URL`. Only allowlisted flags and values are uploaded (`extras.llama_server_args`); other flags and any path-like value are redacted.
- **Exact build and file labels:** `extras.llama_cpp_build` (e.g. `b11803`, null for shallow-clone builds that report build number 1), `extras.llama_cpp_commit`, `extras.llama_cpp_build_source` (server `/props` preferred over local `--version`), `extras.model_file` (GGUF basename) and `extras.model_file_bytes`. Build numbers of any length parse (b11803+). NVFP4 and MXFP4 GGUFs now get a quant label.
- **MLX:** fails fast with `unsupported_arch` when the installed mlx-lm has no module for the model's `model_type` (Flint needs mlx-lm with `models/flint.py`, PR ml-explore/mlx-lm#1998, unmerged as of 2026-10-22).
- **`llm-speed bench --preset flint-40b`:** one command per machine. Detects NVIDIA vs Apple Silicon, picks the quants that fit its memory (others are recorded as skipped, a 16 GB card gets a `--n-cpu-moe` offload probe), finds llama-server (PATH, Homebrew, `~/llama.cpp*/build/bin`) and requires build b11803 or newer, printing the exact install command and asking y/N before running it (no sudo, nothing silent). Checks free disk before each download, downloads from Hugging Face with progress and resume (reuses partial files and the HF cache), runs 4K, 16K and 32K context (stops climbing at the first failure), records every OOM / failed load / skip, prints a summary table, then uploads through the usual consent flow (`--strict-anon` honoured). Rerunning resumes; Ctrl-C stops the servers and keeps finished steps. A model is deleted after its steps only if the preset downloaded it and the next model needs the space. `--with-control` adds the Qwen3.8-27B control. Model repos, pinned revisions, sizes and per-machine context ladders (up to 262K on the RTX 5090 and 64 GB+ Macs, MLX long-context decay at 32K and 131K, disk-gated Q8_0 on Macs) live in `cli/presets/flint-40b.json` (versioned). `llm-speed preset hash <name>` prints the sha256 of the preset's canonical serialization for review-then-publish; `llm-speed preset show|list` too.
- `long-context-decay` honours `$LLM_SPEED_DECAY_CTX` (e.g. `131072`) to measure only those context points.
- **fit_attempts records:** the preset (and the shared fit sweep, `cli/fit_sweep.py`, moved here from Launch Lab's tool) writes one row per attempt in the shape of the site's `fit_attempts` table plus Flint columns (time to first answer, reasoning tokens, `n_cpu_moe`, driver major, llama.cpp build/commit, GGUF basename, baseline memory). Saved locally as `fit_attempts.json`; uploaded to `/v1/fit-attempts` once the site accepts them (until then the CLI says so and keeps them local). Every string passes the path sanitizer.
- **Recorded context = the context that ran.** Each fit step records the llama-server's real `n_ctx` (from `/props`) or, on MLX, the tokens actually processed; the planned step is kept as `context_requested`. A workload that would not fit a step is not run in it (chat-long needs ~5.4K tokens, so it never runs in a 4K step), and if the server reports a smaller `n_ctx` than requested the workloads are re-picked for it. The preset's MLX steps are now 4K chat-short, 8K chat-long, and decay at 32,000 and 128,000 tokens.
- **Upload hard guard.** Every upload path refuses, with the reason, when `LLM_SPEED_OFFLINE=1` is set, or when the environment is synthetic (a test runner, `MOCK_*` variables, a mock/fixture `nvidia-smi` or `llama-server`, or `LLM_SPEED_SYNTHETIC=1`) and the target is not a reserved test host (localhost, `*.test`, `*.example`, `*.invalid`). `--resume` honours `--no-upload`. Fit-sweep records from such environments carry `"synthetic": "<reason>"` and the preset will not upload them.
- `--resume` with `--strict-anon` now sends no User-Agent, like a fresh strict-anon upload.
- llama-server boot timeout raised from 60 s to 600 s (`LLM_SPEED_LLAMA_BOOT_TIMEOUT_S`); `--log-disable` is no longer passed so failures can be explained.

Consent, `--strict-anon`, `--anon`, local-save and `--no-upload` behavior are unchanged. New uploaded fields are listed in `cli/launch_telemetry.py` `UPLOADED_EXTRAS_KEYS` and docs/PRIVACY.md.
